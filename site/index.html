xmss-solidity verifies XMSS signatures (RFC 8391, NIST SP 800-208) entirely inside the EVM, in pure Solidity — and it is proven to compute exactly what the RFC specifies, for every possible input.

Why this exists

A large enough quantum computer breaks ECDSA, and with it every Ethereum account, multisig and bridge key. The replacements standardized so far are lattice schemes, which cost tens of millions of gas to verify — or hash-based schemes, which the EVM can check directly.

XMSS is hash-based. Its security rests on SHA-256 alone: no new assumptions, no pairings, no trusted setup, no oracle, no new precompile. Verification is a few thousand SHA-256 calls, which the EVM already has.

Most signature code is trusted because it passed its tests

This one is also proven. An executable transcription of RFC 8391 sits beside the verifier, and Halmos proves the two compute the same thing — not on sample inputs, on all of them, with SHA-256 treated as an abstract function.

The RFC, as runnable code

Every verification algorithm of RFC 8391 is transcribed line by line, citing its section, and reviewed against the published errata.

Proven equal, for all inputs

Each building block — the hash chain, RAND_HASH, the WOTS+ digits, the L-tree, each tree level, H_msg, the input checks, the height binding — is proven equal to its RFC algorithm.

Checked against foreign code

The test vectors are accepted by the RFC authors' own C implementation, and tampered copies rejected — code this project did not write.

Use it

import {XMSS} from "xmss-solidity/XMSS.sol";

contract MyVerifier {
    // XMSS is stateful: each leaf signs exactly once
    mapping(bytes32 => mapping(uint32 => bool)) public leafUsed;

    function check(
        bytes32 digest,
        XMSS.Signature memory sig,
        bytes32 root,
        bytes32 seed,
        uint256 treeHeight
    ) external {
        bytes32 key = keccak256(abi.encode(root, seed, treeHeight));
        require(!leafUsed[key][sig.leafIdx], "leaf used");
        require(
            XMSS.verify(digest, sig, XMSS.PublicKey(root, seed), treeHeight),
            "invalid XMSS signature"
        );
        leafUsed[key][sig.leafIdx] = true;
    }
}

Three rules for callers

  1. Consume each leaf once per key. The library is stateless. Two signatures under one leaf index let an attacker forge.
  2. Pass the key's registered height. RFC 8391's public key carries an OID that fixes the tree height; PublicKey does not, so the four-argument verify takes it from you.
  3. Bind the context into the digest. Sign an EIP-712 digest covering the chain id, your contract and a nonce, so a signature cannot be replayed elsewhere.

Not audited. The verifier is formally verified against RFC 8391, which is not the same as an audit. Signing and key generation happen off-chain, in hardware that never reuses a leaf.

Questions

What does “formally verified” mean here, exactly?

That the compiled verifier computes the same result as an executable transcription of RFC 8391's verification algorithms, for every input, with SHA-256 modelled as an abstract function. It does not mean XMSS is secure (that rests on published cryptographic proofs), nor that the library is audited, nor that gas never runs out.

Why XMSS and not ML-DSA or Falcon?

Lattice verification costs tens of millions of gas on the EVM today. XMSS verification is pure hashing, so it runs in about 0.7M gas with the SHA-256 precompile that already exists. The trade-off is that XMSS is stateful: each key signs a fixed number of times, and each leaf exactly once.

Is one key enough for production use?

At h = 20 a key signs 1,048,576 times, and the signer tracks which leaf comes next. The contract side must also record consumed leaves, which is one bitmap write per signature.

Where do the signatures come from?

Off-chain. The repository ships a Python implementation of RFC 8391 for key generation, signing and test vectors. Production signing belongs in a hardware device that commits its leaf counter before releasing a signature.
